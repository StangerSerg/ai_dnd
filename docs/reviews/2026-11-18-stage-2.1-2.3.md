## P1 · Предварительно найденный факт теряется перед публичным ответом

Игрок спрашивает об общедоступном факте вне текущей сцены. Поиск находит точный ответ, планировщик видит его и выбирает допустимый `stay`. В журнал хода попадают только индекс входа, `stay` и пустой список событий. Вызов повествования получает этот журнал, а найденный текст туда не попадает. Отдельный `lookup_lore` способен передать текст через результат инструмента, но для уже найденного ответа оснований повторять поиск нет. [Подготовка планирования](../../backend/src/ai_dnd/game/master.py#L244) · [Запись stay](../../backend/src/ai_dnd/game/master.py#L570) · [Вызов повествования](../../backend/src/ai_dnd/game/master.py#L365) · [Контекст повествования](../../backend/src/ai_dnd/game/context.py#L221)

Root подставил поисковик с уникальным публичным фактом и записал сообщения через scripted gateway. При обычном ходе со `stay` факт присутствовал в `dm_tools` и отсутствовал в `narration`. Исправление должно сохранить публичные сведения для последнего сообщения повествователя и учитывать видимость при передаче. Проверка после исправления должна охватить `stay` без дополнительного инструмента и скрытый фрагмент.

## P1 · Локализованные имена статблоков прерывают индексацию five-guardians

Схема допускает имя статблока в виде словаря языков. В `five-guardians.ru.yaml` именно так записаны шесть имён. При нарезке имя передаётся в `_join`, который вызывает у него `.strip()`. Обычный `seed --scenario five-guardians --lang ru` доходит до этого пути после фиксации опубликованной версии. Индексация завершается до записи фрагментов. [Схема имени](../../backend/src/ai_dnd/scenarios/schemas.py#L56) · [Данные кампании](../../content/scenarios/five-guardians.ru.yaml#L1995) · [Обработка имени](../../backend/src/ai_dnd/rag/chunking.py#L108) · [Вызов strip](../../backend/src/ai_dnd/rag/chunking.py#L82)

Офлайн вызовы штатных `load_game_content → _entities → chunk_entity` на файле кампании дали `AttributeError: 'dict' object has no attribute 'strip'`. Root повторил проверку для всех шести статблоков. Следует выбирать перевод имени и особенностей для языка версии с тем же правилом запасного языка, которое использует игра. При повторной проверке все шесть должны дать текстовые фрагменты.

## P1 · Предыдущая версия без подходящих фрагментов даёт неполный индекс

Если v1 опубликовали без индекса или индексировали другой моделью той же размерности, запрос предыдущих сущностей всё равно возвращает их данные. Запрос предыдущих фрагментов фильтрует по имени модели. При равных данных сущности код безусловно переходит к следующей даже при пустом списке для копирования. Полное совпадение сущностей v1 и v2 оставляет v2 с нулём фрагментов. При повторной индексации существующей v2 операция удаления и фиксации заменит её прежний индекс неполным. [Условие переиспользования](../../backend/src/ai_dnd/rag/index.py#L68) · [Фильтр модели](../../backend/src/ai_dnd/rag/index.py#L113) · [Замена индекса](../../backend/src/ai_dnd/rag/index.py#L85)

Root вызвал `index_version` на подставной сессии БД для одной равной сущности без пригодных фрагментов. Отчёт содержал `entities=1, chunks=0, reused=0, embedded=0`. Следует копировать совместимый индекс и рассчитывать эмбеддинги для сущностей без него. Для проверки нужны версии без индекса и с предыдущей моделью, а также повторная индексация версии с уже заполненным индексом.

## P2 · Публикация не ставит задачу в очередь воркера

`publish_scenario` фиксирует текущую версию и возвращает UUID. Команда `seed` затем вызывает `index_version` в процессе CLI без идентификатора предыдущей версии. Даже идентичная публикация пересчитывает все эмбеддинги. При `seed --no-index` шаг пропускается целиком, хотя справка обещает индексацию воркером. Постановка задачи в очередь доступна отдельной командой `reindex`. Это расходится с критерием готовности 2.2. [Завершение публикации](../../backend/src/ai_dnd/scenarios/store.py#L201) · [Индексация в CLI](../../backend/src/ai_dnd/console.py#L549) · [Справка](../../backend/src/ai_dnd/console.py#L570) · [Постановка задачи](../../backend/src/ai_dnd/console.py#L597)

Root и Astra независимо проследили оба пути CLI. Для выполнения критерия следует связать успешную публикацию с надёжной постановкой задачи, передавать предыдущую версию для переиспользования и согласовать с этим семантику флага. Приёмочный прогон должен начинаться с публикации и заканчиваться готовым индексом воркера без ручного вызова второй команды.

## P2 · Команда reindex --wait скрывает ошибку воркера

Когда задача индексации завершается исключением, Taskiq возвращает объект результата с признаком ошибки. CLI читает только `return_value`, выводит «Результат воркера: None» и завершается с кодом успеха. Поэтому оператор или вызывающий скрипт может принять упавшую индексацию за успешную. [Ожидание и вывод результата](../../backend/src/ai_dnd/console.py#L600)

Astra и Root отдельно вызвали `_reindex` с подставной очередью и результатом Taskiq, в котором `is_err=True`, `error=ValueError(...)` и `return_value=None`. Оба вызова штатно завершились. Следует проверять статус через `raise_for_error()` и возвращать ненулевой код при ошибке задачи.
